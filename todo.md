# py8dis: to do

Ideas for improvements, roughly in order of value (19 Nov 2026).

1. **What subroutines leave behind.** At the moment nothing is known after a JSR. Some facts about a subroutine don't depend on how it was called: which registers and flags it never writes (so a caller's X, say, is still known after the call), and what's known at every one of its RTSs (e.g. the carry is always clear). Carry these past each JSR to it, and note them in the subroutine's "On Exit" notes where a caller relies on them. *(Done 19 Nov, including registers and flags saved on the stack and got back: see docs/cpus.md.)*

2. **Suggest control-file lines for what py8dis can't prove.** Where a jump table's dispatch is found but its index can't be bounded (e.g. anfs418 &8c93/&a13b/&a997, dfs226 &8740/&b238, Open ROMs &fe0a, memory128), or a table is rejected (e.g. Open ROMs BASIC's overlapping token tables), print a suggestion, e.g. `# probable RTS jump table at $a4c9, X not known: rts_code_ptr(...)`, ready to paste into the control file. *(Done 19 Nov: a note for each table whose index isn't known, with the entries it seems to have (see docs/cpus.md). The examples had two, anfs418 &a99d (9 entries) and Open ROMs kernal &fe0e (17), which their control files now mark. Notes for tables found but rejected done 20 Nov: the note says which entry is wrong and why (it points into data, inside an instruction or into the table, or overlaps another entry), with the lines that would mark the entries before it, or for a table of words whose index can be odd, its even entries. None occur in the examples; the test jump_tables has one of each kind. Doing so found that a jump table entry pointing inside a string or an instruction's operand crashed find_jump_tables().)*

3. **Size data tables, not just jump tables.** The index ranges already say e.g. that `sine_table,y` has 32 entries and `bit_table,x` 8. Mark such tables as data of that length and say what indexes them. Find pointer tables used as `lda lo,x : sta ptr : lda hi,x : sta ptr+1 : lda (ptr),y`, and write their entries as label expressions, as is done for jump tables. *(Done 19 Nov: see docs/cpus.md, "Data tables". The examples get 164 tables of bytes, 3 of words, and no tables of pointers: the two found are in RAM or already marked by their control files.)*

4. **Track known values in zero page as well as registers.** E.g. after `lda #<buf : sta ptr : lda #>buf : sta ptr+1`, a memory loop through `(ptr),y` could say "Clear 256 bytes of memory from buf onwards" rather than "from (l0074)", and a jump table whose index was stored in zero page first could be found. The effect patterns already know some memory within a straight run; this would bring it into the joined states. *(Done 20 Nov: each byte of zero page is a set of values, as the registers are, through stores, loads, INC/DEC/shifts, arithmetic and compares, indexed and through known pointers, across calls to subroutines that don't write it (see docs/cpus.md). A loop keeps only the bytes it writes and its pointers, so polling loops aren't 'ALWAYS branch'; I/O and the 6510's port aren't tracked. Tables read through a known pointer are sized, and the pointer's immediate loads written as '#<label'/'#>label', as are those before a memory loop. In the examples: penetrator's sprite tables sized exactly (8 bytes, not 64, and 4 more found), a table in OS 1.20, an always-taken BPL in the Atom kernel, and four CLCs where the carry is already clear (chuckie, the Atom's floating point ROM). Done 20 Nov too: zero page is shown in the CPU state ('[70]:05') and the JSON's cpu_state ('zero_page'); and subroutine()'s new zero_page_written says which zero page addresses a subroutine may write, so what's known about the rest is kept after a call to it, even outside the binary: acorn.bbc() gives &90-&FF for OSWRCH, OSASCI, OSNEWL, OSRDCH and OSBYTE (the Advanced User Guide gives &00-&8F to the language), and c64() and vic20() $90-$FF for the Kernal calls that say what they preserve (see item 10). Not done: pointer_loads() still stops at any JSR, even one that doesn't write the pointer.)*

5. **Stop tracing past "ALWAYS branch" when the bytes are clearly data.** OS 1.20 &f581 is still disassembled as code, though the same code reads it as a table (`ora cf581,y`). If what follows an always-taken branch is also read as indexed data, prefer data. (Stopping on the branch alone is riskier, since code there may be reached in ways py8dis doesn't see.) *(Done 20 Nov: once the states are known, code traced only by running on past a branch that's always taken is taken back when the code reads it as a table and, as code, it runs straight into an opcode that doesn't exist (or the 6510's JAM) within the table, with no branch, jump, call or return in it and nothing else reaching it (Cpu6502.drop_traced_data()); find_data_tables() then marks it. OS 1.20 &f581 is now "A table of 7 bytes, indexed by Y (0 to 6)", and it's the only change in the examples: the other always-taken branches into tables (dfs226's NMI code at &0d60, copied with 'lda $0d60,x', and its code copied to the stack at &bf8b) are real code, which runs into another branch rather than a bad opcode. Done 20 Nov too: the '; overlapping' comments for the instructions tracing found only by running on past an always-taken branch into data that's already classified are taken back (Cpu6502.drop_overlaps_after_always_branches()), if they all just read or write memory or change the registers and nothing else reaches them. The Atom kernel's &f6cf loses its two, and the labels l0086 and le298 that only they used; nothing else in the examples changes.)*

6. **More loop comments.** Search loops, e.g. memory128's "Search key_table (16 bytes) for A". On the 65C02, `stz table,x` loops are memory clears that the set-loop snippets don't yet recognise (basic4 is 65C02 code). *(Done 20 Nov: snippets for loops that search with X or Y as the index and the count (CMP table; LDA and BEQ/BNE, for 0; LDA and CMP #value), e.g. "Search 16 bytes from key_table for A", "Search 256 bytes from (os_text_ptr) for $0d", "Search 40 bytes from buffer for a byte other than $20", or in terms of the register where its first value isn't known ("Search X+1 bytes from table for A"); and STZ loops, as for STA ("Clear 128 bytes of memory from l0480 onwards"). The examples get 21 search comments in 11 of them (memory128, OS 1.20, DFS 2.26, ANFS, the Atom's kernel and BASIC, Open ROMs, penetrator...) and basic4 two clears. Also for loops that set memory: an operand the code changes is 'the address in' the label of its bytes, if the loop starts there (planb's was named as the operand assembled), and otherwise gets no comment; and the first byte is e.g. 'table3 + 1' where the operand's address has a name of its own, rather than a new label. See docs/snippets-and-hooks.md, and the example search_loops. Done 20 Nov too: searches can index with one register and count with the other ('cmp table,y : beq found : iny : dex : bpl loop'), and loops that compare two runs of bytes ('lda a,x : cmp b,x : bne differ', or EOR) are commented, e.g. "Compare 5 bytes from float8B_exponent with float8A_exponent": 10 in the examples (ANFS, the Atom's floating point ROM, basic4, LISP, Open ROMs, OS 1.20). The end of a range not known is e.g. 'l1000 + 63' rather than a new label. (CPX and CPY have no indexed modes, so 'cpx table,y' isn't a thing.) Not done: compare loops that index the two runs with different registers (OS 1.20 &dac5, the Atom's DOS &e178).)*

7. **Speed.** Joining the states at labels made the big ROMs 1.4 to 1.7 times slower, since every tracing pass works out every state again. Working out only what changed since the last pass should recover most of that. The full test suite takes about 210s. *(Done 20 Nov, with the output unchanged: the big ROMs take 55-80% of the CPU time they did (dfs226, dfs226b and lisp406 about 55%), and the full test suite 210s rather than 310s. go() runs without Python's cyclic garbage collector, which went through every object kept, again and again, while the states were worked out; the states aren't worked out again when tracing from the entry points found from what the code does finds nothing new (as for dfs226, planb and lisp406); joining the states at labels works out only what's known for certain; what doesn't depend on the state is kept for each instruction while they're worked out; b2r() keeps its answers; and check_expr() looks constants up by name. The CPU state tests take 40s rather than 145s. Not done: working out only what changed when something has (how loops are widened depends on the order the states are worked out in, so the result could differ); the output side (fix_label_names() and emit()), now about a third of the time (looked at 20 Nov: about 0.5s of 1.5s for dfs226 and anfs418, spread over building the lines, formatting and naming, with nothing that stands out).)*

8. **The Z80.** The known bits, ranges, joins at labels and jump tables are all 6502-only. The Z80's state tracking could get the same (the Spectrum ROM, bbcbasic and opense would benefit). The biggest item here.

9. **Sets of values.** *(Done 19 Nov: each register is known as the set of values it could have, a 256-bit mask (py8dis/valuesets.py), instead of its known bits and range. The operations are exact, ranges wrap round (so after 'ldx #16 : loop: ... dex : bpl loop' X is 0 to 16 at the loop and $ff after it), ASL keeps the values above $7f (A is the even values $9e to $fe after 'cmp #$cf : bcc skip : asl'), and joins keep e.g. 0 or $80. py8dis now finds Open ROMs kernal's table of control code routines (&fe0e) itself, since it knows X is 0 to 16 there, so the control file only labels it.)*

10. **What OS routines preserve.** *(Done 19 Nov: a subroutine()'s on_exit descriptions of exactly '(preserved)', '(clear)' or '(set)' are taken as what's known after a call to it, wherever it is (Cpu6502.declared_exits()), and acorn.bbc() declares them for OSWRCH, OSASCI, OSNEWL (A, X, Y preserved, D clear) and OSRDCH (X, Y preserved, D clear). Done 20 Nov too: OSBYTE preserves A (the Advanced User Guide, and MOS 1.20's code); on the C64 and VIC-20, the Kernal calls preserve the registers that neither the Programmer's Reference Guide's 'Registers affected' nor the Kernal's code (sta.c64.org's 'Used registers') changes, e.g. X and Y for CHROUT, so a loop that prints with CHROUT keeps its counter (commodoretables.kernal_preserved_registers). Not done: OSWORD (only MOS 1.20's code says it preserves A); the Atom's and Apple's routines, and the C128's, Plus/4's and PET's Kernals, for which I didn't find documentation that says.)*
