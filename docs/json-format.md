# py8dis JSON output (version 1)

As well as the asm, py8dis can write the finished disassembly as JSON, for other tools to read: e.g. a web page of the disassembly with links between labels and the code that uses them, a symbol table for an emulator's debugger, or a comparison of two versions of a ROM.

```
python3 mycontrolfile.py --acme --json out.json              # asm printed as usual, JSON to out.json
python3 mycontrolfile.py --acme -o out.asm --json out.json   # asm to out.asm, JSON to out.json
```

`--json` doesn't need `-o`: the asm goes wherever it would anyway (printed, or to the `-o` file), and the JSON goes to its own file. When using py8dis as a library, `session.new_session(json_filename="out.json")` does the same.

The JSON holds everything py8dis knows once it has finished: the names are exactly those in the asm, but there's no layout (columns, hex dump, word wrapping). `py8dis-json.schema.json`, next to this file, is a [JSON Schema](https://json-schema.org/) for it.

## Conventions

- **Addresses are integers** (a label can be at 65536, just past the top of memory). py8dis distinguishes a *binary address* (where a byte is in the loaded data) from a *runtime address* (where it is when the program runs, after any `move()`). Every address says which it is. A `move_id` says which move applies, and is left out when it's 0 (not moved).
- **Ranges** are `{"start": ..., "end": ...}`, from `start` up to but not including `end` (so `end` can be 65536).
- **Optional keys are left out** when empty or not applicable.
- **Text** (an expression, an instruction, a value) is given as in the asm, in the syntax of the assembler chosen for the run (`assembler`). The structured data next to it doesn't depend on the assembler.
- **Order** is fixed, so files can be compared: items by binary address, labels by runtime address, and a label's names in the order the asm defines them.
- **Versions:** `version` changes only if a reader of the old format could misread the new one. New keys can be added without changing it, so a reader should ignore keys it doesn't know.

## Top level

```jsonc
{
  "format": "py8dis",
  "version": 1,
  "cpu": "6502",                        // "6502", "65c02", "6510" or "8080"
  "assembler": "beebasm",               // "acme", "beebasm", "xa" or "z88dk"
  "loads": [ { "filename": "orig/helloworld.orig", "start": 8192, "end": 8220 } ],
  "moves": [ { "id": 1, "binary_addr": 8208, "runtime_addr": 2304, "length": 18 } ],
  "constants": [ { "name": "newline", "value": 13, "text": "&0d",
                   "comment": { "text": "...", "align": "inline" } } ],
  "memory_regions": [ { "start": 0, "end": 256, "name": "Zero page" } ],
  "subroutines": [ { "runtime_addr": 8194, "name": "print", "title": "Print a string",
                     "description": "...", "on_entry": { "x": "offset" }, "on_exit": { "a": "corrupted" } } ],
  "labels": [ ... ],
  "items":  [ ... ],
  "range_boundaries": [ ... ]
}
```

- `loads` are the files loaded with `load()` or `load_prg()`, in the order loaded: the filename as given, and the binary addresses the data is loaded at. `offset` is where in the file the data loaded starts, if it isn't the start of the file (with `load(..., offset=...)`, or after a PRG file's two-byte header). `prg` is `true` for a PRG file loaded with `load_prg()`; if it's the lowest load, the asm starts with the file's two-byte header, so that it assembles to the whole file.
- `constants` are in the order the asm defines them. `text` is the value as the asm shows it, and `comment` the constant's comment, if any.
- `memory_regions` are those in effect (the CPU's, acorn.py's and the control file's, after any renaming or removal), as used to group "Memory locations" in the asm, by start address, larger first.
- `subroutines` are those given with `subroutine()` that are in the loaded data, or whose names the asm uses (e.g. the OS calls acorn.py names, when they're called). Each has the `runtime_addr`, its `move_id` if any, and whichever of `name`, `title`, `description`, `on_entry` and `on_exit` were given.
- A constant's `value` is usually an integer, but can be a string (e.g. `constant("1900", "page")`).

## Labels

One for each address with a name, inside or outside the loaded data:

```jsonc
{
  "runtime_addr": 65518,
  "names": [
    { "name": "oswrch", "autogenerated": false,
      "definition": "memory_locations", "memory_region": "MOS entry points" }
  ],
  "local_names": [ { "name": "loop", "output_name": "loop_2", "start": 8194, "end": 8203, "memory_region": "Zero page" } ],
  "expressions": [ { "text": "table+1" } ],
  "references": [ { "binary_addr": 8197, "runtime_addr": 8197 } ]
}
```

- **`names`:** in the order the asm defines them. Each has a `move_id` if it's for a move, and says whether py8dis made it up (`autogenerated`, e.g. `l2000`, `pydis_start`). `definition` says where the asm defines it: `inline` at its address, `relative` to the label at the start of the item it's inside (e.g. `l2001 = c2000+1`), `memory_locations` as `name = value` at the top (with the `memory_region` heading it's under, the region's name or `Other`, if there are headings), or `none` if the asm doesn't define it.
- **`local_names`:** from `local_label()`, each used only by the code in its range of binary addresses, from `start` up to but not including `end`. `output_name` is the name the asm uses, when different. The asm defines them under "Memory locations" (with `memory_region` as for `names`).
- **`expressions`:** from `expr_label()`.
- **`references`:** each instruction, byte or word that refers to the address: its binary address, and the runtime address it runs at.
- A label is listed only if it has a name, a local name or an expression.

## Items

One for each instruction or piece of data, in binary address order. Together they cover the loaded data exactly, with no gaps or overlaps.

```jsonc
{
  "binary_addr": 8194, "runtime_addr": 8194, "length": 3,
  "bytes": [189, 14, 32],
  "labels": ["loop_c2002"],                     // the names the asm defines here, in order
  "comments": [ { "text": "Print the message", "align": "before_line" } ],
  "type": "instruction",
  "text": ["lda message,x"],                    // as in the asm, one string per line

  "mnemonic": "lda",
  "mode": "absolute_x",
  "operand": { "value": 8206,
               "expr": { "text": "message", "tree": { "label": 8206, "name": "message" } } },
  "cycles": "4/5",
  "cpu_state": { "a": null, "x": 0, "y": null, "n": null, "v": null, "d": null, "i": null, "z": null, "c": null }
}
```

All items have `binary_addr`, `runtime_addr`, `length`, `bytes` (a list of integers), `type` and `text`, and `move_id`, `labels` and `comments` when there are any. A comment's `align` is one of `before_label`, `after_label`, `before_line`, `inline` or `after_line`, as given to `comment()`. Its text is as given, before word wrapping. It has `"autogenerated": true` if py8dis wrote it (e.g. "referenced 2 times by", a subroutine's header, or `A=value` for a subroutine's argument), and a `kind` if it isn't an ordinary comment: `overlapping` for an instruction found while tracing that overlaps the code or data there (e.g. `overlapping: lda l001e`), or `raw` for text added with `annotate()`, output as it is. The comments are those for each of the item's bytes in turn.

The `type`s are:

- **`instruction`:**
  - `mnemonic`, as in the asm (upper or lower case, as chosen). For the 8080 it's just the mnemonic: register operands (e.g. `mvi b,`) are only in `text`.
  - `mode`, the addressing mode. For the 6502 and 65C02: `implied`, `accumulator`, `immediate`, `zp`, `zp_x`, `zp_y`, `zp_indirect`, `zp_x_indirect`, `zp_indirect_y`, `absolute`, `absolute_x`, `absolute_y`, `indirect`, `absolute_x_indirect` or `relative`. For the 8080: `implied`, `immediate`, `immediate16` or `address`.
  - `operand` (unless implied): its `value` (an address or an immediate value) and its expression.
  - `target`: for a branch, jump or call, the runtime address it goes to.
  - `undocumented`: `true` for an undocumented opcode, e.g. the 8080's &CB, which runs as JMP, or the 6502's (with the CPU `"6510"`), e.g. &A7, LAX zp. Where the assembler doesn't accept it (all of them except some of the 6502's with acme), the asm writes it as data bytes (`text`), with the instruction in a comment. `mnemonic`, `mode`, `operand` and `target` are those of the instruction it runs as.
  - `cycles`, as `config.set_show_cycles(True)` shows them, e.g. `"2/3"` for a 6502 branch (not taken, or taken), or `"5/11"` for an 8080 conditional return (`"halts"` for the 6502's undocumented JAM). Always included.
  - `cpu_state`: what py8dis knows for certain about the registers and flags once the instruction has run, as `config.set_show_cpu_state(True)` shows it: registers as numbers, flags as `true` or `false`, and `null` where it's not known. For the 6502 and 65C02 that's `a`, `x`, `y` and the flags `n`, `v`, `d`, `i`, `z`, `c`; for the 8080, `a`, `b`, `c`, `d`, `e`, `h`, `l`, `sp` and the flags `s`, `z`, `ac` (auxiliary carry), `p`, `cy`. Always included for the instructions py8dis traced (it's useful even when the asm doesn't show it).
- **`bytes`** and **`words`:** `values`, and `exprs` with an expression for each value given with `expr()`, or `null`. `exprs` is left out if there are none.
- **`string`:** the `text` shows it as in the asm. `encoding` is `"petscii"` or `"screen"` (Commodore screen codes) for a string in that encoding (see `config.set_text_encoding()`); it's left out for ASCII.
- **`include_binary`:** `filename`, the file included with `include_binary_file()`.

## Range boundaries

At the start or end of a range of the output (the loaded data, or a move's data), the asm can define labels and give comments with no item for them. For example, in a program that copies some of its code elsewhere with `move()`, the label for the source of the copy is defined just before the moved code, and `pydis_end` is defined after the last item:

```jsonc
"range_boundaries": [
  { "binary_addr": 8222, "runtime_addr": 8222, "labels": ["c201e"],
    "comments": [ { "text": "&201e referenced 1 time by &2002", "align": "before_label", "autogenerated": true } ] }
]
```

Each has `binary_addr`, `runtime_addr` and `move_id` (when not 0), and `labels` and `comments` as for an item. Only those with labels or comments are listed, by binary address then move.

## Expressions

An expression is `{"text": ..., "tree": ...}`: the text as in the asm, and the expression as a tree. The tree's nodes are:

| Node | Example |
|---|---|
| number, with its `format`: `decimal`, `signed_decimal`, `hex` (2 or 4 digits as needed), `hex2` or `hex4` (that many digits), `binary`, `picture_binary` or `char`; left out if py8dis doesn't know (e.g. a control file's own formatter) | `{"num": 13, "format": "hex"}` |
| name (e.g. a constant) | `{"name": "newline"}` |
| label: its runtime address, and the name used here (usually one of the label's names, but it can be an expression relative to another label, e.g. `brkv+1`) | `{"label": 8206, "name": "message"}` |
| an expression written as a string in the control file (not parsed) | `{"raw": "<sprite0"}` |
| unary operator | `{"op": "<", "arg": {...}}` |
| binary operator | `{"op": "+", "left": {...}, "right": {...}}` |

Operators use py8dis's names, whatever the assembler: unary `<` (low byte), `>` (high byte) and `NOT`; binary `+`, `-`, `*`, `DIV`, `MOD`, `AND`, `OR`, `EOR`, `<<` and `>>`. Any other name given to `make_op1()` or `make_op2()` is passed through as it is.
